# qrbeam v1 の実装上のワイヤ形式

これは `docs/spec.md` 1.1 を補足する実装記録です。暗号方式の外部審査や実機評価の完了を示すものではありません。

## 共通フレーム

QRの内容はフレーム全体のRFC 9285 Base45文字列です。独自プレフィックスはありません。QR英数字モードを使います。Base45の空白はデータなので、読み取り結果を `trim()` してはいけません。

数値は特記しない限り符号なし・ビッグエンディアンです。

| オフセット | バイト数 | 内容 |
|---|---:|---|
| 0 | 4 | ASCII `QRBM` |
| 4 | 1 | プロトコル版 `1` |
| 5 | 1 | メッセージ種別（下表） |
| 6 | 1 | MACフラグ。`0` または `1` |
| 7 | 16 | セッションID。HELLO/HELLO_ACKは全ゼロ |
| 23 | 4 | 方向ごとに0から増加するシーケンス番号 |
| 27 | 2 | ペイロード長 |
| 29 | 可変 | ペイロード（最大2048バイト） |
| 29+長さ | 0または16 | HMAC-SHA-256の先頭16バイト |
| 末尾-4 | 4 | CRC-32/ISO-HDLC |

MACの対象はオフセット0からペイロード末尾まで（MACフラグを含む）です。CRCはMACがあればMACも含めた直前の全バイトが対象です。CRCパラメータは反転多項式`0xEDB88320`、初期値と最終XORは`0xFFFFFFFF`。末尾の余分なバイト、不正な長さ、未知の版・種別・フラグは拒否します。

## ペイロード

ロールはsender=`1`、receiver=`2`。端末nonce、SAS nonce、転送ID、セッションIDは各16バイト。公開鍵はSEC1非圧縮P-256の65バイト。ハッシュとファイルダイジェストは32バイトです。

| 種別番号 | 名称 | ペイロード（順番に単純連結） |
|---:|---|---|
| 1 | HELLO | ロール1 + 自端末nonce16 + 機能版1（値`1`） |
| 2 | HELLO_ACK | ロール1 + 自端末nonce16 + 受信した相手端末nonce16 |
| 3 | KEY | 公開鍵65 |
| 4 | KEY_ACK | 受信した公開鍵のSHA-256 32 |
| 5 | COMMIT | 受信側コミットメント32 |
| 6 | NONCE | 送信元のSAS nonce16 |
| 7 | READY | 送信元ロール1 + トランスクリプトハッシュ32 |
| 8 | START | 転送ID16 + GCM nonce12 + 暗号文長4 + 分割バイト数2 + 分割数4 + パディング単位4 |
| 9 | DATA | 転送ID16 + 分割インデックス4（0始まり）+ 暗号文断片 |
| 10 | ACK | 転送ID16 + base4 + ビット数2 + ビットマップ |
| 11 | NACK | ACKと同じ形。ビットの意味のみ反転 |
| 12 | FIN | 転送ID16 + 分割数4 |
| 13 | COMPLETE | 転送ID16 + 鍵付きファイルダイジェスト32 |
| 14 | CANCEL | 非機密のASCII理由コード |
| 15 | ERROR | 非機密のASCII理由コード |

STARTの分割サイズは128〜1024バイト、分割数は`ceil(暗号文長 / 分割サイズ)`と一致する必要があります。パディング単位は両端末の設定が一致する必要があります。既定は4096です。実ファイル名・サイズ・平文SHA-256はDATA内の暗号化されたエンベロープだけに含めます。

ACKの`base`未満の全分割は受信済みです。ビット数は最大256で、`base`から続く分割に対応します。バイト内ではLSBからインデックスが増えます。ACKでは`1`が受信済み、NACKでは`1`が欠落を示します。末尾の未使用ビットはゼロです。ACK/NACKはそれまでに処理した確認フレームより新しいシーケンス番号だけを採用し、古いNACKの再生で進捗や保存待ち期限が巻き戻ることを防ぎます。DATAは順序逆転を許可し、同一インデックスの内容変更を拒否します。

## 鍵合意と再表示

暗号式の`||`は、各要素の前に32ビットのバイト長を付ける連結です。文字列はUTF-8（ラベルはASCII）、トランスクリプトのプロトコル版は1バイトの`0x01`です。HKDF saltの`N_S || N_R`だけは固定長16+16バイトの単純連結です。HKDF infoは用途ラベル全体（例`qrbeam-v1 mac s2r`）とTHをそれぞれ長さ付きで連結します。

双方のHELLOとHELLO_ACKが必要です。nonceのロール順を固定してセッションIDを計算します。相手の公開鍵を検証した受信側だけがCOMMITを生成します。送信側はCOMMIT受信後だけN_Sを生成・開示し、受信側はN_S受信後だけN_Rを開示します。

再表示はキャッシュした同一フレームです。鍵・nonce・コミットメントは再生成しません。最後のNONCEが読み取られずに鍵合意が停止するのを防ぐため、既に生成した鍵合意フレームは相手のREADYを確認するまで再表示候補として残します。これらは最初の生成時点ではMACなしで、鍵導出後に受信したMACなしのHELLO〜NONCEは状態を変更しません。READY以降、および鍵導出後に新規生成するCANCEL/ERRORは方向別MACで検証します。

送信側は、相手が自分のREADYをまだ読み取れていない場合にも備え、STARTのACKを受信するまでREADYとSTARTを交互に再表示します。受信側のSTART受理には、自分の承認と検証済み相手READYの両方が必要です。遅れて到着したREADYは転送中に承認タイマーを再設定しません。

送信側は未確認分割のうち先頭から設定ウィンドウ内を巡回表示します。全分割のACKを受けてFINを表示します。受信側は全分割とFINの後に復号・検証し、保存待ちになります。保存取消や書込み失敗ではCOMPLETEを生成しません。保存の`close()`成功後だけ生成したCOMPLETEは、終了操作まで同じ文字列を再表示します。送信側はMACと転送IDとダイジェストの一致後だけ完了になります。

セッション終了時は鍵・平文・暗号文の参照を破棄し、可能なバッファは上書きします。保存後の受信側に残すCOMPLETEは事前計算したフレーム文字列で、秘密鍵の保持は不要です。JavaScriptとブラウザの完全なメモリ消去を保証するものではありません。
