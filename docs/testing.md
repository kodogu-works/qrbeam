# qrbeam 検証手順と実機試験記録

この文書は `docs/spec.md` §12〜§14 の受け入れ試験を行うための手順である。自動テストや合成QR画像のベンチマークは、2台の実機による光学転送、`file://` でのAPI動作、OSごとの対応確認を代替しない。

現時点では、以下のOS・ブラウザの実機試験は未実施であり、対応バージョンと最低ハードウェア要件は確定していない。第三者暗号レビューと組織の利用承認も別途必要である。

## 開発環境での自動検証

リポジトリのルートで実行する。

```sh
npm ci
npm run check
npm run benchmark
```

`npm run check` は型チェック、単体・プロトコル結合テスト、単一HTMLのビルド、成果物検査を実行する。個別の結果と実行環境はその実行ログを保存する。失敗した検証を未実施・成功として記録しない。

ブラウザE2Eは次のコマンドで実行する。

```sh
npx playwright install chromium
npm run test:browser
```

開発環境のLinux / Chromium 141.0.7390.37で、配布HTMLを`file://`で2ページ開き、オフラインコンテキストのE2Eが成功した。カメラはcanvasの映像、保存先は待機・取消を注入できるモックを使用し、QR生成・映像からの同梱jsQR読取り・Web Crypto・UIは実装をそのまま実行した。SAS一致、Enter保持・リピート拒否、片側承認での送信抑止、保存取消からの再試行、`close()`待ち中の未完了、保存後の双方完了、512バイトの完全一致を確認した。HTTP要求、CSP違反、ページエラーはいずれも0だった。

モックなしの初期画面でも、同Chromiumの`file://`でsecure context・Web Crypto・カメラAPI・File System Access APIの公開を確認した。実カメラの許可や読み取り、ネイティブ保存ダイアログと実ディスク書き込みを自動試験したものではないため、以下の実機マトリクスは未実施のままとする。

初期実装の最終検証では、型チェック、9ファイル81件の単体・結合テスト、上記ブラウザE2E 1件、成果物検査が成功した。同一ソースから続けて生成したHTMLのSHA-256も一致した。`npm audit --omit=dev`の指摘は0件だった。

配布HTMLのコピーを一時的なQA専用OpenPGP鍵で署名し、元ファイルの検証成功と1バイト変更後の検証失敗を確認した。QA鍵は試験後に破棄し、`dist/qrbeam.html`に正式なリリース署名は付けていない。組織の責任者の鍵による署名・別経路での公開鍵配布は、正式リリース時の作業として残る。

`npm run benchmark` はBase45とBase64について、テキスト変換、QR生成、同梱デコーダによる合成画像の読取りを比較する。実カメラ、照明、画面の残像、ローリングシャッター、ネイティブ `BarcodeDetector` の性能は測定しない。繰返し回数は `QRBEAM_BENCH_ITERATIONS`（1〜100、既定5）で指定できる。

続いて、10 KiB・100 KiB・1 MiB、ウィンドウ1・2・4・8のプロトコルシミュレーションを実行する。モデルは512バイトDATA、4 KiBパディング、表示350 ms、片方向遅延175 ms、両方向それぞれ約5%の決定的なフレーム欠落である。承認操作と保存成功は模擬するため、UI・実カメラ・保存APIの試験ではない。`simulatedSeconds` はモデル上の経過時間、`cpuSeconds` はソフトウェア実行時間として区別する。`QRBEAM_BENCH_PROTOCOL=0` でこのシミュレーションを省略できる。

```sh
QRBEAM_BENCH_ITERATIONS=20 npm run benchmark
```

## 2台のPCを使うオフラインE2E試験

機密情報を含まない試験用バイナリを用意する。0バイト、10 KiB、100 KiB、1 MiB、上限超過の1 MiB+1バイトを含める。内容は全ゼロ、繰返しデータ、任意バイナリを組み合わせる。試験用ファイルのバイト比較やSHA-256照合はQAの手順として行い、その平文ハッシュをアプリの監査ログに追加しない。

1. 両PCのWi-Fi、EthernetなどのネットワークアダプタをOS側で無効化し、外部DNS・外部接続が利用できない状態にする。アプリの接続状態表示だけで判定しない。
2. ブラウザの開発者ツールで、アプリ由来の外部要求とCSP違反が発生しないことを確認する。ログを保存する場合はQRペイロード、試験用でないファイル名や内容を含めない。
3. Aを「送信」、Bを「受信」にする。Aで1ファイルを選び、双方で「次へ・カメラを許可」を押す。
4. 相手のQR全体がカメラに入るように調整する。双方がHELLOを確認し、鍵交換を経て同じ6桁コードを表示することを確認する。
5. 一方だけ「コードが一致・開始」を押し、DATA転送が始まらないことを確認する。もう一方でも6桁を目視照合して承認する。
6. 進捗が進み、Bで「保存」が表示されることを確認する。この時点ではAが「転送完了」を表示してはならない。
7. Bで保存し、保存が成功した後にのみBが「検証成功・保存済み」、Aが認証済みCOMPLETEの受信後に「転送完了」を表示することを確認する。
8. 保存したバイナリを元のファイルとバイト単位で比較する。同一セッションの双方の画面・監査ログで、セッションIDとHMACファイルダイジェストが対応することを確認する。監査ログ識別子は端末ごとに異なる。
9. BのCOMPLETEは終了操作まで表示されること、双方の「終了」後はカメラが停止することを確認する。
10. 送受信を入れ替え、OSの異なる組合せでも繰り返す。1 MiB+1バイトは転送開始前に拒否されることを確認する。

## 光学条件とウィンドウの比較

初期値はBase45、DATA容量512バイト、QR誤り訂正M、ウィンドウ1、最小表示間隔350 msである。UIのQR表示サイズは小300・中420・大600 CSSピクセルを目安とし、実際の領域幅に応じて縮小されるため、試験時には実測値を記録する。画面の拡大率も記録する。

1条件につき少なくとも3回、新規セッションで転送する。同じ組合せでウィンドウ1・2・4・8を比較し、他の要因は固定する。その後、DATA容量128・256・512・768、表示間隔、誤り訂正L/M/Q/H、画面の明るさ、距離、QRサイズ、カメラ解像度を1要因ずつ変更する。両PCの設定を揃える。最低条件は成功例だけでなく失敗境界を含めて決める。

| 条件ID | PC組合せ | ファイル | 距離cm | 輝度%/照明 | QR実寸・位置 | カメラ実解像度 | DATA/ECC/間隔ms | ウィンドウ | 成功/試行 | 鍵合意秒 | 転送秒 | 保存・完了秒 | 再表示回数 | 実効B/s |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 基準-W1 | 未測定 | 10 KiB/100 KiB/1 MiB | 未測定 | 未測定 | 中・中央/未測定 | 未測定 | 512/M/350 | 1 | 未測定 | 未測定 | 未測定 | 未測定 | 未測定 | 未測定 |
| 基準-W2 | 未測定 | 同上 | 同上 | 同上 | 同上 | 同上 | 512/M/350 | 2 | 未測定 | 未測定 | 未測定 | 未測定 | 未測定 | 未測定 |
| 基準-W4 | 未測定 | 同上 | 同上 | 同上 | 同上 | 同上 | 512/M/350 | 4 | 未測定 | 未測定 | 未測定 | 未測定 | 未測定 | 未測定 |
| 基準-W8 | 未測定 | 同上 | 同上 | 同上 | 同上 | 同上 | 512/M/350 | 8 | 未測定 | 未測定 | 未測定 | 未測定 | 未測定 | 未測定 |

鍵合意時間は位置合わせ開始からSAS表示まで、転送時間は双方承認から受信検証成功まで、保存・完了時間は検証成功から送信側の完了表示までを分けて測る。実効速度は実ファイルのバイト数を転送秒で割る。試験記録の実サイズはQA用であり、アプリ監査ログのサイズ省略方針とは別に管理する。

UIの再表示回数は、カメラで失われたフレーム数そのものではない。QR読取率・再送率が必要な場合は機密データを用いず、表示と検出の件数のみを試験用に計測し、定義を記録する。100 KiBを数分以内に転送する目標は実測で判断し、達成を前提にしない。

## 誤操作・障害・攻撃の試験

| 試験 | 操作・注入 | 必須の結果 |
|---|---|---|
| Enter持越し | S4になる前からEnterを押し続ける | 1,500 ms経過だけでは承認されず、keyup後の新しい非repeat keydownとボタンフォーカスが必要 |
| Enter早押し・リピート | S4直後のEnter、キーリピート、他の要素にフォーカス | 承認しない。S4後のガードを満たした明示操作だけを受け付ける |
| フォーカス喪失 | S4で別ウィンドウへ切替後に戻る | 押下中として扱い、keyup確認なしにEnter承認しない |
| 片側のみ承認 | もう一方を承認しない | 機密DATAを送らず、承認待ち期限超過で中止 |
| 認証不一致 | 異なるコードで「コードが違う・中止」 | 継続せず新規セッションを要求。連続2回で警告・監査イベント |
| 自己反射・同ロール | 自分のHELLOを撮影、双方を送信に設定 | 自己HELLOを無視。同ロールは通知し、再選択を案内 |
| QR欠落・重複・順序逆転 | 片側画面を断続的に遮蔽、同じQRを連続撮影 | 未受信分を再送し、重複で副作用や破損が起きない |
| ACK/NACK/FIN | ACKを遮蔽、古いACKを遅延、欠落状態のFIN、FIN重複 | 選択的再送、同じACKの継続表示、検証処理の冪等性を保つ |
| 保存取消 | 保存ダイアログを取り消す | COMPLETEを送らず、保存再試行または中止が可能 |
| 保存書き込み・close失敗 | 満杯の試験用保存先、書込み不可先、テストでclose拒否を注入 | 成功と表示せず、COMPLETEを送らない。再試行可能 |
| 保存中止・待ち期限 | 保存前に中止、保存処理中にセッション終了、保存待ち期限超過 | 後から保存Promiseが解決しても終了セッションを復活させず、送信側は未保存/完了未確認 |
| COMPLETE消失 | Bの保存後にAのカメラを遮蔽 | BはCOMPLETEを継続表示。Aは受信検証まで完了せず、期限超過で完了未確認 |
| カメラ障害 | 権限拒否、外付けカメラ抜去、映像停止 | 案内を表示し、安全に中断。再開には新規セッション |
| 遮蔽の継続 | 長時間QRを隠す | 配置修正を案内し、再表示回数・時間の上限で中止 |
| タブ・電源障害 | リロード、タブ終了、スリープ、試験端末停止 | 既存セッションを再開しない。受信未検証ファイルを提供しない |
| セッション寿命 | 短縮設定またはテスト用時刻で期限超過 | 秘密鍵・導出鍵の参照を破棄し中止 |
| フレーム改変 | CRC、MAC、SID、sequence、長さを改変 | 不正入力を受理しない。READYの認証失敗は中止 |
| 鍵合意改変 | 不正公開鍵、COMMIT前のNONCE、コミットメント不一致、交換値の変更 | 不正公開鍵・コミットメント不一致で中止。未検証SASを表示しない |
| リプレイ・反射 | 別セッションQR、送信したREADY/COMPLETEを反射 | 相手の承認・完了として受理しない |
| 暗号文改変 | 認証付き経路を含む試験ハーネスで暗号文またはAADを変更 | GCM認証失敗で保存禁止。ハッシュ不一致も保存禁止 |
| 危険な名前 | NFD、予約名と拡張子、パス区切り、末尾空白、UTF-8境界 | NFC化、安全な保存候補名、255バイト以内。機密内容をプレビューしない |
| 配布物改変 | 署名後のHTMLを試験コピーで1バイト変更 | 署名・ハッシュ検証に失敗し起動禁止 |

改変QRやMAC付き異常入力の試験は、単体・結合テストまたは専用の非配布ハーネスで行う。配布アプリへテスト用鍵、認証迂回、ネットワーク経路を追加しない。

## 試験完了の判定と記録

試験記録には実施者、日時・タイムゾーン、環境、設定、期待結果、実測結果、証跡、未解決事項を残す。送受信方向を含む全対象構成で、オフライン転送、バイト一致、双方承認、保存後完了、異常時の未完了扱いが確認できた範囲だけを対応済みとする。

運用担当者による署名確認とコード照合の手順試験、第三者による暗号・実装レビュー、大学側の取扱規程との照合・承認を完了してから、正式導入を判断する。
