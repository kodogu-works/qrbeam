# qrbeam 配布・利用・監査の運用手順

現時点の成果物は開発版である。Windows/macOS/Linux実機での対応確認、第三者暗号レビュー、大学・組織の利用承認は未完了であり、正式導入の承認を示すものではない。対応環境の資格確認は [testing.md](testing.md) に従う。

## 配布責任者による準備

正式成果物は `dist/qrbeam.html` の単一HTMLである。実行時のJavaScript・CSS・QRライブラリはHTMLに埋め込まれ、追加のファイルやCDNを要求しない。ビルド時の依存取得は開発環境で事前に行い、配布する実行環境にNode.jsやnpmを導入する必要はない。

```sh
npm ci
npm run check
```

配布対象のソースコミット、`package-lock.json`、Node.js/npmとOSのバージョン、検証結果を保存する。ビルドに使う依存関係を固定し、同じ入力から再ビルドしたHTMLのSHA-256が一致することを確認する。日時を含む署名ファイル自体のバイト一致は再現可能ビルドの判定対象にしない。

生成された `dist/SHA256SUMS` をHTMLとともに配布する。`dist/build.json` にはビルド識別子、HTMLのSHA-256、同梱依存の一覧が出力される。S0に表示されるビルド識別子とHTMLのSHA-256を、責任者が管理する配布手順書にも掲載する。ビルド識別子だけでは改ざんを検出できないため、署名とハッシュを併せて確認する。

署名鍵は組織の配布責任者が所有・管理する。以下のコマンドは既存鍵で配布物に署名する。アプリやビルド処理は署名鍵を自動生成しない。秘密鍵をリポジトリやHTMLへ含めない。

```sh
node scripts/sign.mjs minisign /secure/qrbeam-release.key
```

または、責任者の既存OpenPGP鍵を使う。

```sh
node scripts/sign.mjs gpg RELEASE_SIGNING_KEY_ID
```

署名スクリプトは成果物検査を実行してから、minisignでは `dist/qrbeam.html.minisig`、OpenPGPでは `dist/qrbeam.html.asc` を生成する。配布責任者は生成後に自分でも署名を検証し、HTML・SHA256SUMS・署名・手順書を同一リリースとして管理する。署名後にHTMLを変更した場合は、検証・ハッシュ生成・署名からやり直す。

公開鍵またはその指紋は、配布物とは別の信頼できる経路で利用者へ渡す。HTMLと同じ未検証の配布場所から初めて入手した公開鍵だけを信頼しない。鍵管理者、更新・失効時の連絡方法、配布手段、第三者レビュー実施者は組織が確定する。

## 各PCで起動前に行う検証

責任者から受け取った検証ツールと公開鍵を事前に準備する。以下は配布ファイルを置いたディレクトリで実行する例であり、鍵のパスやIDは組織の値に置き換える。

minisign署名の場合:

```sh
minisign -Vm qrbeam.html -p /trusted/qrbeam-release.pub
```

OpenPGP署名の場合、別経路で指紋を照合済みの公開鍵を使う。

```sh
gpg --show-keys --with-fingerprint /trusted/qrbeam-release-public.asc
gpg --import /trusted/qrbeam-release-public.asc
gpg --verify qrbeam.html.asc qrbeam.html
```

署名の検証成功に加え、署名鍵の指紋が組織指定の責任者のものか確認する。知らない鍵による有効な署名を受け入れない。

ハッシュを確認する。Linuxの場合:

```sh
sha256sum -c SHA256SUMS
```

macOSの場合:

```sh
shasum -a 256 -c SHA256SUMS
```

Windows PowerShellの場合:

```powershell
(Get-FileHash .\qrbeam.html -Algorithm SHA256).Hash.ToLower()
Get-Content .\SHA256SUMS
```

PowerShellでは計算された64桁の値を `SHA256SUMS` の `qrbeam.html` 行と比較する。責任者の手順書に記載されたハッシュとも照合する。未認証のハッシュファイルだけでは配布元の確認にならない。

署名、ハッシュ、指定された鍵のいずれかが一致しなければ、そのHTMLは起動せず責任者へ報告する。検証に使ったコマンドの終了コードと対象リリースを運用記録に残す。

## 2台のPCでの転送

1. 組織が確認したPC版ChromeまたはEdgeを用意する。スマートフォン・タブレットは対象外である。アプリのAPI検出が成功しても、その環境の実機試験完了を意味しない。
2. 両PCで署名・ハッシュを検証する。ネットワークアダプタをOS側で無効化し、周囲から画面を撮影・覗き見されない場所に置く。アプリのネットワーク状態表示だけに頼らない。
3. `qrbeam.html` を直接開き、`file://` のアドレスとS0のビルド識別子を確認する。必要なAPIが使えない表示の場合は、その環境を使用しない。
4. 送信PCで「送信」を選び、1 MiB以下、UTF-8で255バイト以内の名前の1ファイルを選ぶ。受信PCで「受信」を選ぶ。
5. 必要なら開始前の「通信設定」を両PCで合わせる。通常は既定値を使う。双方で「次へ・カメラを許可」を押す。
6. 相手の画面全体ではなく、相手のQR全体が自分のカメラに映るように調整する。明るさ、距離、角度、QRの表示サイズ・位置、使用カメラを調整できる。読み取り中もカメラとQRの両方を見える状態に保つ。
7. 両画面の6桁コードを直接見て比較する。一致したときだけ、双方で「コードが一致・開始」を操作する。Enterは同ボタンへフォーカスし、S4表示から1,500 msを経過し、押し続けたEnterを離した後の新しい押下のみ有効となる。
8. コードが違う場合は「コードが違う・中止」を押し、新規セッションからやり直す。同じセッションで続行しない。不一致またはコミットメント検証失敗が連続2回になると警告するため、組織の情報セキュリティ担当者へ報告する。
9. 転送中は両PCの画面とカメラを維持する。受信側で検証が成功したら、表示された候補名とサイズを確認し「保存」で保存先を選ぶ。内容のプレビューや自動実行は行わない。
10. 保存ダイアログの取消や書き込み失敗では、保存を再試行するか中止する。保存未完了では完了通知を送らない。受信側は書き込みの `close()` 成功後に「検証成功・保存済み」を表示する。
11. 送信側の「転送完了」を確認する。受信側の保存成功だけでは送信側の完了確認は成立しない。受信側は送信側がCOMPLETEを読み取れるようQR表示を維持する。
12. 必要な双方の監査ログを「監査ログを保存」で保存してから、各PCで「終了」を押す。終了後はカメラが停止し、そのセッションは再開できない。

通常の進捗表示にはパディング済み暗号文のバイト数が用いられるため、元ファイルの実サイズと一致しないことがある。

## 初期設定

以下の値は実機による性能・操作性評価前の暫定値である。設定を変えた場合は運用手順と実機試験記録に残す。設定はセッション開始前に変更する。

| 項目 | 初期値 | UIでの変更 |
|---|---|---|
| QR内テキスト | Base45・英数字モード | 固定 |
| DATA容量 | 512バイト | 128/256/512/768 |
| ウィンドウ | 1枚 | 1/2/4/8 |
| QR誤り訂正 | M | L/M/Q/H |
| 最小フレーム表示間隔 | 350 ms | 150〜3,000 ms |
| 鍵交換待ち | 120秒 | 30〜600秒 |
| 承認待ち | 180秒 | 30〜600秒 |
| 保存待ち | 300秒 | 60〜900秒 |
| セッション有効期限 | 60分 | 10〜120分 |
| 同一フレームの最大再表示回数 | 100 | 10〜1,000 |
| SASのEnterガード | 1,500 ms | 固定 |
| 暗号化前パディング | 4 KiB単位 | 固定 |
| 監査ログへの実サイズ記録 | なし | 固定 |

1 MiBは上限であり、転送時間の保証ではない。保存待ちなどの期限を超えた場合は、ファイルを完成扱いにしない。後から相手が保存できたか不明な場合は「完了未確認」として扱い、双方の操作者が結果を確認する。

## 失敗・中断した場合

カメラの権限拒否、機器の切断、読取不能、認証不一致、復号失敗、期限超過では、画面の原因を確認して転送を中止する。配置の問題は距離・角度・明るさとカメラ選択を見直す。認証やコミットメントの失敗を通常の読取り失敗と同一視しない。

保存できていない状態で中止すると、送信側は受信側の未保存として扱う。受信側が保存済みでもCOMPLETEを送信側が検証できなければ、送信側は完了未確認となる。受信側で保存した事実を確認し、重複ファイルができる可能性を考慮して、新規転送の要否を操作者が判断する。

リロード、タブ終了、PCの停止、セッション終了後には途中転送を再開できない。新規鍵合意と再照合から始める。障害の報告に機密ファイル名・内容・QRペイロードを添付しない。ビルド識別子、監査ログ識別子、OS/ブラウザ、機密を含まない理由コードを使う。

## 監査ログの保管

ログはメモリ上で作成され、ユーザーが「監査ログを保存」を明示的に操作したときだけ、File System Access APIでローカルのJSONファイルへ書き出す。終了・再読み込み前に必要なログを保存する。自動アップロードや自動永続化は行わない。

JSONにはログ識別子、セッションID、ビルド識別子、ロール、開始時刻とイベント時刻、許可されたイベントと結果、セッション内のHMACファイルダイジェストを含める。時刻は端末設定に依存し、JSONではUTCのISO 8601形式となる。ファイル名、本文、平文のSHA-256、実ファイルサイズは含めない。

ファイルダイジェストはセッション固有の監査鍵によるHMAC-SHA-256であり、同じセッションの送受信記録を照合するための値である。後日ファイル本体のSHA-256と照合したり、別セッションの同じファイルを識別したりするためには使えない。組織管理鍵による後日の照合機能は初期実装に含めない。

ログ自体は署名付きの耐改ざん記録ではなく、第三者証明を提供しない。機密扱いとし、保管先、アクセス権、保管者、保存期間、廃棄方法を組織の監査規程で定める。ログの署名や集中保管が必要な場合は別の運用手順を設ける。

ブラウザの `localStorage` は連続認証失敗回数（`qrbeam.sasFailures`）の記録にのみ使用する。ファイル・鍵・QR・途中データ・監査ログを保存しない。`file://` でのストレージ動作や利用可能性はブラウザに依存し、利用できない場合の警告回数はページ内だけで保持する。端末全体にわたる確実な失敗回数管理ではない。

## 導入前に組織が確定する事項

実機で動作確認したOS・ブラウザのバージョン、画面・カメラの最低要件、外付けカメラの扱い、第三者暗号レビューの担当者と方法、署名鍵の管理者と公開鍵の別経路配布、監査ログの保管規程、大学の情報取扱規程との整合と利用承認を確定する。

秘密鍵・導出鍵は非抽出として生成し、終了時に参照を破棄する。平文バッファは可能な範囲で上書きするが、ブラウザ・OS全体のメモリ消去を完全保証するものではない。端末侵害、OSやブラウザの通信、画面の盗撮、操作者の誤認に対する端末管理と運用審査は別途必要である。
